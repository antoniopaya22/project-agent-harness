# Harness entrypoint — read this first, always

You are working in a repository managed by **harness v1**. This file is the only one you read
unconditionally. It tells you where everything is and what the hard rules are. Do not explore the
repository to orient yourself — follow the read path below.

## Cold-start read path

To work on task `<ID>`, read exactly these, in order, and stop:

1. **this file**
2. `.harness/backlog/tasks/<ID>.json` — the task. It is the **router**: `context.area`,
   `context.docs` and `context.files` tell you what else to read. Nothing outside that list is
   relevant unless you discover otherwise while working.
3. `.harness/project.json` — gates (how to lint/test/build), areas, git conventions.
4. `docs/areas/<context.area>.md` — the slice of architecture this task touches.

Then read only what `context.docs` and `context.files` name. If you find you need more, that is a
signal the task was under-groomed: note it in the task's worklog.

`docs/CODEMAP.md` answers "where does a new X go?". Read it only when you must create new files and
the area doc does not say where. `docs/CONVENTIONS.md` is the style authority — read it once per
session at most, never per file.

## Hard rules

- **Never guess a command.** Lint, test, build, format and start commands live in
  `project.json.gates` and are invoked as `harness gate <name>`. If a gate is `not-configured` or
  `n/a`, skip it and say so; do not invent a substitute.
- **Never edit a generated file.** Anything whose first lines contain `GENERATED by harness` is
  produced by `harness generate` from `.harness/`. Edit the canonical source in `.harness/` and
  regenerate.
- **Never mark a task `done`.** Only a human can. Agents move tasks up to `in_review`.
- **Never weaken, skip, delete or `xfail` a test to make a gate pass.** If a test fails, either the
  code is wrong or the test is wrong; say which, with evidence, and stop.
- **Never edit `acceptance_criteria` of a task you are implementing.** They are the contract. If they
  are wrong, stop and say so.
- **Never commit on a protected branch** (`project.json.git.protected_branches`).
- **Secrets never enter task files, docs, or commits.** Config holds ids; tokens live in `.env`.

## Output language

Deliverables — documentation, task titles and descriptions, commit bodies, reports to the user —
are written in the language of `project.json.project.output_language`. These instruction files are
in English; that does not license English output.

## Task lifecycle

```
backlog --groom--> ready --claim--> in_progress --verify--> in_review --human--> done
                                        |  ^                     |
                                        v  +---------------------+
                                     blocked            (changes requested)
```

Entry conditions are enforced by `harness task set-status`, which refuses illegal transitions:

| status        | requires                                                              |
|---------------|-----------------------------------------------------------------------|
| `ready`       | >=1 acceptance criterion with a `check`, `context.area` set, deps done |
| `in_progress` | a branch, an `assignee`, `claimed_at`                                 |
| `blocked`     | `blocked_reason`                                                      |
| `in_review`   | required gates green, every criterion `pass` or justified              |
| `done`        | human only                                                            |
| `cancelled`   | human only, `resolution` set                                          |

## Where your output goes

| What | Where |
|------|-------|
| Implementation plan | `.harness/workspace/<ID>/plan.md` |
| Research notes | `.harness/workspace/<ID>/research.md` |
| Verification verdict | `.harness/workspace/<ID>/verification.md` |
| Review verdict | `.harness/workspace/<ID>/review.md` |
| Stage handoff (survives context loss) | `.harness/workspace/<ID>/handoff.json` |
| Anything else | a file the task's acceptance criteria name |

Before doing anything expensive, check whether `handoff.json` already exists: if it does, **resume
from its `stage`** instead of starting over.

## Commands

`harness` is the deterministic CLI (`node .harness/bin/harness.mjs`, or the `harness` shim).

| Command | Purpose |
|---------|---------|
| `harness task list\|show\|next\|new\|claim\|set-status\|retype\|split` | backlog operations |
| `harness gate <name>` | run a declared quality gate |
| `harness index` | regenerate `backlog/index.json` and `BOARD.md` |
| `harness validate` | tasks against the schema |
| `harness lint-backlog` | duplicate ids, dependency cycles, orphan parents, unready `ready` |
| `harness generate [--check]` | (re)write provider adapters from `.harness/` |
| `harness doctor [--fix]` | validate the harness itself, including read-path budgets |
| `harness status` | one-screen situational awareness |
| `harness sync [--dry-run]` | project the backlog to the external tracker (optional) |

Slash commands (`/implement`, `/commit`, `/plan`, `/verify`, `/review`, `/task`, `/adopt`, `/status`,
`/doctor`, `/handoff`) are the agent-facing wrappers, defined in `.harness/commands/`.

## Agents

Six roles, defined in `.harness/agents/`: `planner`, `implementer`, `tester`, `reviewer`,
`researcher`, `scribe`. Each declares what it writes and what it is forbidden from touching. If you
are one of them, your own definition overrides nothing here — it narrows it.
