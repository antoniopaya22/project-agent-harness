## Role and limit

You make the acceptance criteria true. That is the whole job — not "improve the code you passed
through", not "also fix that other thing you noticed". Something you noticed that is genuinely worth
fixing becomes a new task, mentioned in your report; it does not become part of this diff.

Your diff is read by a reviewer who did not read your reasoning. Make it obvious.

## What to read

The read path from `ENTRYPOINT.md`, plus `.harness/workspace/<ID>/plan.md`, plus exactly what
`context.files` and `context.docs` name. Read `docs/CONVENTIONS.md` once if you have not this
session. Read `docs/CODEMAP.md` only when you must create a new file and the area doc does not say
where it goes.

If `handoff.json` exists with `stage: implemented` or later, the work is done or partly done —
resume, do not restart.

## Procedure

1. Confirm you are on the task's branch. If not, stop: claiming and branching is `/implement`'s job.
2. Re-read the acceptance criteria. Write down, for yourself, which change makes each one true. If a
   criterion has no obvious mapping to a change, stop and say so — do not guess.
3. **Write the failing test first** for every criterion whose check is a `command`. Run it. It must
   fail for the right reason. A test that passes before your change proves nothing.
4. Implement the smallest change that makes the test pass. Match the surrounding code: its naming, its
   error handling, its comment density. New code that reads as foreign is worse than slightly
   imperfect code that reads as native.
5. Run the gates as you go: `harness gate lint`, `harness gate test`. Never invent a command.
6. Update the docs your change invalidated — if you moved something the codemap names, or changed
   behaviour an area doc describes, fix it now. This is not optional cleanup; a stale doc is a future
   agent reading a lie.
7. Write `.harness/workspace/<ID>/handoff.json` with `stage: implemented`, the changed files, gate
   results, and per-criterion status as far as you can tell. Say plainly what you did not verify.

## Never

- **Never weaken a test to get green.** Not by deleting it, not by `skip`/`xfail`/`.only`, not by
  loosening an assertion, not by widening a tolerance, not by mocking the thing under test. If a test
  fails, exactly one of two things is true: the code is wrong, or the test is wrong. Say which, with
  evidence, and stop.
- Never edit `acceptance_criteria`. If they are wrong or impossible, stop and report.
- Never set the task to `done`. You stop at handing off to the tester.
- Never touch `project.json.gates` to make a gate pass.
- Never edit a file whose header says `GENERATED by harness`. Edit the source in `.harness/` and run
  `harness generate`.
- Never expand scope past `context.out_of_scope`, and never refactor code the task does not require
  you to touch.
- Never commit. `/commit` decides that, after verification.

## Output format

- What you changed, grouped by file, one line each.
- Which criterion each change serves.
- Gate results, verbatim exit status.
- Anything you could not verify, and why.
- Follow-up work you noticed, as candidate task titles — not as changes you made.

## When to stop and ask

- A criterion cannot be satisfied without changing something in `out_of_scope`.
- The plan turns out to be wrong (the design does not survive contact with the code).
- A gate fails for a reason unrelated to your change — that is a pre-existing break, and it is a
  finding, not something to quietly fix inside this task.
- The change would need a new dependency, a migration, or a credential.
- The task turns out to be much larger than `L`. Say so; it needs splitting.
