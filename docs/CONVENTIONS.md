# Convenciones

> La autoridad de estilo de este repositorio. Si el código hace algo consistentemente y este documento
> no lo prohíbe, gana el código.

## Código

- **JavaScript moderno, módulos ESM, extensión `.mjs`.** Sin TypeScript y sin paso de build: el tooling
  tiene que ejecutarse en cualquier proyecto sin instalar nada (D2).
- **Cero dependencias.** Solo la stdlib de Node, importada con el prefijo `node:`. Añadir una dependencia
  requiere un ADR.
- **Un módulo, una responsabilidad**, y como máximo 600 líneas — el gate `lint` lo comprueba. Cuando un
  fichero se pasa, se parte por responsabilidad, no por la mitad.
- **Sin clases** salvo para errores (`HarnessError`). Funciones puras cuando se pueda; efectos de disco
  concentrados en `util.mjs`.
- **Comentarios que explican el *por qué*.** El *qué* ya lo dice el código. Un comentario que parafrasea
  la línea siguiente se borra. Los que valen son los que explican una decisión no obvia o una trampa.
- **Nombres en inglés en el código** (identificadores, ficheros de definición). Texto de cara al usuario
  y documentación en español (D8).

## Errores y salida

- Fallo esperado → `fail(mensaje, EXIT.<CÓDIGO>)`. Nunca `process.exit` desde dentro de un comando: se
  devuelve el código y el dispatcher sale.
- Los códigos de salida son contrato, porque hooks y CI se ramifican con ellos:
  `0` ok · `1` algo que el usuario debe arreglar · `2` invocación incorrecta · `3` rehusado por
  precondición · `4` no encontrado.
- Los mensajes de error dicen **qué hacer a continuación**, no solo qué ha fallado. Compara
  "transition backlog -> done is not allowed (from backlog you may go to: ready, blocked, cancelled)"
  con "invalid transition".
- Salida por `say`/`ok`/`bad`/`warn`/`info` de `util.mjs`, nunca `console.log` directo: el color se
  desactiva solo cuando no hay TTY o hay `NO_COLOR`.

## Escritura de ficheros

- Todo lo generado se escribe con `writeFileIfChanged` o `writeJson`, que normalizan a LF y no tocan el
  fichero si el contenido no cambia. **La estabilidad byte a byte no es cosmética**: `generate --check`
  y `doctor` comparan contenidos, y un timestamp dentro de un fichero generado rompería la detección de
  deriva. Por eso ningún fichero generado lleva fecha.
- Todo fichero generado abre con la cabecera `GENERATED by harness`.

## Tests

- `node:test` y `node:assert/strict`. Ficheros en `tests/*.test.mjs`.
- Un test prueba **comportamiento observable**, no implementación. Si renombrar una función privada
  rompe el test, el test estaba mal.
- Los tests que tocan disco trabajan sobre un directorio temporal propio y lo limpian.
- **Un test nunca se debilita para que pase.** Ni `skip`, ni aserción relajada, ni mock de lo que se está
  probando. Si falla, o el código está mal o el test está mal: se dice cuál.

## Git

**Ramas**: `<tipo>/<número>-<slug>` → `feat/0042-registro-usuario`.
El tipo ya está en el id de la tarea (`FEAT-0042`), así que **no se repite** en la rama.
Tipos: `feat` · `fix` · `chore` · `docs` · `refactor` · `test` · `spike`.

**Commits**: `<tipo>(<ámbito>): <asunto>`

- Asunto en imperativo, ≤72 caracteres contando el prefijo, sin punto final.
- Cuerpo explicando **por qué**, no qué (el diff ya dice qué).
- Trailer `Refs: FEAT-0042`, o `Closes: FEAT-0042` en el commit que cierra la tarea.
- Ámbitos válidos: los de `git.commit_scopes` en `.harness/project.json`.
- Commits incrementales durante `/implement`: cada hito es un punto de recuperación.

Ejemplos válidos:

```
feat(cli): añadir harness read-path para acotar la lectura en frío
fix(schema): aceptar parent nulo en tareas sin epic
```

No válidos: `update stuff` (no dice nada) · `feat: Añadida la funcionalidad.` (no imperativo, con punto)
· `fix: arreglar bug` sin `Refs:` (no se puede rastrear a una tarea).

**Nunca**: commitear en una rama protegida · `git push --force` sin decirlo · commitear con un gate
requerido en rojo salvo `--no-verify` explícito y anotado · mergear un PR desde un agente.

## Cómo escribir una comprobación

Estas dos reglas salieron de equivocarse en las dos direcciones, y valen para cualquier check nuevo.

- **Un check imposible de satisfacer es peor que ningún check.** Entrena a la gente a ignorar la salida
  entera. Si la condición no se puede cumplir en algún caso legítimo —el fichero no tiene dónde poner la
  marca, el proyecto acaba de nacer— ese caso es un aviso con su propio mensaje, no el mismo error.
- **Un aviso no puede sostener un criterio de aceptación**: `doctor` y los gates salen con 0 ante avisos.
  Si un criterio dice «el autodiagnóstico lo comprueba», entonces o el check es de nivel error, o el
  criterio no está comprobado por nada. Lo mismo con `node --test --test-name-pattern`, que sale con 0
  cuando no casa ningún test.
- **Distingue «falló» de «no se pudo ejecutar»** antes de decidir el nivel. Son dos problemas con dos
  arreglos distintos, y juntarlos produce mensajes que no dicen qué hacer.

## Documentación

- **Un tema, un dueño.** Ningún hecho aparece en dos documentos. Se enlaza, no se repite.
- Cada documento declara al principio qué contiene y qué **no**.
- Front-matter con `updated` y `owner`.
- Presupuestos de líneas del camino de lectura en `read_path` de `.harness/project.json`; `doctor` los
  hace cumplir. Cuando un documento se pasa, se saca contenido — **no se sube el presupuesto**.
- Nada de documentos que existan porque una plantilla tenía un hueco.
